# Filesystem TWYLT Pack 0.6.0

## Миграция 0.6.0

Пак основан на последней версии GitHub, проверенной 2026-10-08.
TWYLT >=1.1.1 устанавливается как библиотека; сам этот пак не собирается и
не устанавливается через pip. Установите requirements.txt и сохраняйте
каталоги tools/ и shared/filesystem_common/ вместе. Если новая версия TWYLT ещё не доступна
в вашем Python-индексе, сначала установите её из исходников или wheel.

Общие guardrails не копируются в инструменты: используются twylt.guardrails.
Каждый тул добавляет shared/ в sys.path относительно __file__, без зависимости
от cwd и без PYTHONPATH. Builder сканирует только tools/; его launcher требует
доступности исходного дерева. Разные версии пака запускайте в отдельных процессах.

Guardrails выключены по умолчанию. Для прежней политики задайте TWYLT_GUARDRAILS=1
и TWYLT_WORKSPACE_ROOT. TWYLT_ALLOWED_CWD опционально разрешает отдельный корень
транспорта input.json/output.json и его подкаталоги; бизнес-доступ он не расширяет.
Отказы guardrails возвращают код 6; валидация — 2, бизнес-ошибка — 5.
При выключенной политике и отсутствии workspace используются обычные пути хоста;
при указанном workspace сохраняется виртуальная семантика путей.
Механизмы TWYLT контролируют типовое использование, а произвольный Python/подпроцессы
контролируются ОС. Не рассматривайте эти проверки как файловую изоляцию.


13 Python-инструментов исходного пака для файловой системы, совместимых с **TWYLT >=1.1.1** и сканированием через ToolPack Builder. Имена имеют префикс `fs_`, чтобы не конфликтовать с другими паками.

## Контроль рабочей области (изменение совместимости)

При `TWYLT_GUARDRAILS=1` обязателен `TWYLT_WORKSPACE_ROOT`; все пути теперь виртуальные относительно него,
включая начинающиеся с `/`. Подробнее: [WORKSPACE.md](WORKSPACE.md), включая
настройку runner, журнал JSONL и границы контроля. Без корня бизнес-операции
отклоняются. Describe продолжает работать без настройки.

## Установка и запуск

Python **3.11+**. Проверено на Linux / Python 3.12. Windows и macOS предусмотрены стандартными файловыми API, но в этой сборке не проверялись. Фильтрация POSIX-прав и владельцев недоступна на Windows; проход через симлинки запрещён политикой области.

```bash
python -m venv .venv
# Linux/macOS
. .venv/bin/activate
# Windows cmd вместо предыдущей строки:
# .venv\Scripts\activate.bat
python -m pip install -r requirements.txt
# Укажите уже созданную рабочую область и существующий каталог журналов:
export TWYLT_GUARDRAILS=1
export TWYLT_WORKSPACE_ROOT=/srv/agent/workspace
export TWYLT_INCIDENT_LOG=/srv/agent/logs/incidents.jsonl
```

С `uv`, без активации окружения (при включённых guardrails задайте те же переменные окружения):

```bash
uv venv
uv pip install -r requirements.txt
uv run --no-project python tools/fs_list/run.py '{"path":".","max_depth":2}'
```

JSON в примерах команд заключён в одинарные кавычки для Bash. В Windows удобнее передать JSON через файл или stdin.

```bash
python tools/fs_list/run.py '{"path":".","max_depth":2,"limit":20}'
python tools/fs_list/run.py '{"describe":"json_spec"}'
python tools/fs_read/run.py < request.json
```

`run.py` использует штатный `twylt.bootstrap.run_tool_file`. Можно запускать и `tool.py` напрямую. Стандартные режимы TWYLT: первый JSON-аргумент, JSON из stdin или `input.json`/`output.json`; describe возвращается в stdout. При аргументе/stdin рабочий результат также возвращается в stdout. Для файлового режима stdin должен быть закрыт/пуст: открытый pipe без данных может ждать EOF (важно для runner ToolHub).

Пример файлового режима:

```bash
# Перейдите в рабочую область и подготовьте input.json, например {"path":"."}.
# Укажите полный путь к установленному run.py:
python /opt/filesystem-pack/tools/fs_list/run.py < /dev/null
# Результат — output.json. В Windows cmd используйте < NUL.
```

Describe поддерживает штатные значения TWYLT: `brief`, `schema`, `few_shots`, `requirements`, `json_spec`. У каждого инструмента есть `name`, `version`, строгие входная и выходная схемы, requirements, few_shots, а также собственный `example.json`.

## Подключение к ToolPack Builder / ToolHub

1. Укажите каталог `tools` и маску **`**/tool.py`**. Не сканируйте `src` и `scripts` как инструменты.
2. Соберите toolpack и импортируйте его в ToolHub обычным способом.
3. Зависимости представлены в `requirements` каждого инструмента. Runner должен завершать stdin после JSON либо использовать уже настроенный вами режим запуска.

Каждый `tools/fs_*/tool.py` содержит контракт и собственную бизнес-логику; общий код загружается из `shared/filesystem_common`. Копируйте tools/ и shared/ вместе. `run.py` нужен для локального bootstrap. `manifest.json` — индекс содержимого этого архива, **не готовый формат импорта ToolHub**.

## Пути и общие правила

- При включённых guardrails пути виртуальные относительно `TWYLT_WORKSPACE_ROOT`, `~` и `..` запрещены.
- `path` и `source` в ответах также виртуальные; `relative_path` — относительно каталога поиска.
- Symlink/junction, файлы с несколькими hard links и специальные файлы запрещены
  для доступа; поиск может показывать метаданные самой ссылки без перехода к цели.
- Неизвестные поля запрещены, типы строгие; ошибки — стандартный механизм TWYLT.
- Нарушения политики пишутся в JSONL и отклоняются. Это контроль обёрток, не ОС sandbox.

## list / find / glob

Общие параметры:

| Поле | По умолчанию | Семантика |
|---|---|---|
| `path` | обязательно | Корневой каталог, сам в результат не входит; конечный симлинк-каталог запрещён |
| `max_depth` | list: `1`; find/glob: `null` | Дочерние объекты — уровень 1; `0` — пусто; `null` — без ограничения глубины |
| `name_regex` | `null` | Python `re.search` по basename; регистр учитывается, `(?i)` его отключает |
| `type` | `null` | `file`, `directory`, `symlink`, `other`; `null` — все |
| `permissions` | `null` | POSIX mode как строка `"644"` или `"0755"`; учитываются и специальные биты |
| `permission_match` | `"exact"` | `exact` — совпадают все биты; `all` — есть все заданные; `any` — хотя бы один |
| `access` | `null` | `"r"`, `"rw"`, `"rwx"` и т.п.; доступ текущего процесса через `os.access` |
| `owner` | `null` | POSIX username строкой либо UID числом; строка `"1000"` означает имя, не UID |
| `include_hidden` | `true` | При `false` исключаются dot-имена и их поддеревья |
| `offset` | `0` | Сколько совпадений пропустить |
| `limit` | `100` | Размер страницы, 1…10000 |
| `on_error` | `"raise"` | `raise` — ошибка; `skip` — пропустить с отчётом |
| `max_entries` | `100000` | Лимит посещённых объектов; при превышении — ошибка, а не частичный успех |
| `include_stats` | `false` | Добавить content-статы обычных файлов возвращаемой страницы |
| `stats_encoding` | `auto` | Кодировка для статов: BOM/UTF-8 либо явное имя codec |
| `stats_max_bytes` | `16777216` | Лимит чтения для статов одного файла, максимум 64 MiB |

`access` отличается от mode-битов: на него могут влиять ACL, привилегии пользователя, особенности ОС; `os.access` использует реальные UID/GID по умолчанию. Для симлинка mode/owner берутся у самой ссылки, а при заданном `access` ссылки пропускаются без проверки цели. `include_hidden` не проверяет Windows hidden attribute.

`find` и `glob` дополнительно принимают `path_regex`: regex по относительному пути с `/`. Все заданные фильтры соединяются через **И**. Фильтр типа/имени не препятствует обходу неподходящих каталогов: `type=file` продолжает поиск внутри них.

`glob` требует `pattern`. Поддержаны `*`, `?`, `[abc]`, `[!abc]`, а `**` отдельным сегментом означает ноль или больше уровней. `*.py` ищет только непосредственно в корне, `**/*.py` — на всех уровнях, включая корень. Только относительные шаблоны с `/`; brace expansion, `~`, extglob и `..` не поддерживаются. Шаблоны регистрозависимы на всех ОС.

### Примеры

Просмотр двух уровней:

```json
{"path":"/work/project","max_depth":2,"offset":0,"limit":100}
```

Следующая страница: тот же запрос, но `offset` равен полученному `next_offset`.

`fs_find`, Python-файлы на любой глубине:

```json
{"path":"/work/project","name_regex":"(?i)\\.py$","type":"file","include_hidden":false}
```

`fs_find`, файлы определённого владельца и с правами группы на чтение:

```json
{"path":"/work/project","type":"file","owner":1000,"permissions":"040","permission_match":"all","access":"r"}
```

`fs_glob`, файлы конфигурации до четвёртого уровня:

```json
{"path":"/work/project","pattern":"**/config*.yaml","max_depth":4,"type":"file","limit":20}
```

`fs_find`, каталоги только в поддереве `src`:

```json
{"path":"/work/project","type":"directory","path_regex":"^src(?:/|$)"}
```

Ответ содержит `entries`, `total`, `offset`, `limit`, `next_offset`, `scanned`, `complete`, `errors`, `error_count`. У объекта: путь, относительный путь, имя, тип, глубина, размер в байтах из `lstat`, `modified_ns`, octal mode, UID и имя владельца. Размер каталога не равен сумме его содержимого.

Порядок детерминированный: сначала все отсортированные по имени непосредственные дети каталога, затем поддеревья каталогов по имени. **Каждый запрос заново обходит дерево**, чтобы посчитать `total`. Страницы стабильны только при неизменном дереве; это не snapshot и не курсор базы данных. При `skip` поле `total` относится к успешно просмотренным объектам, `complete=false`, первые 100 ошибок перечислены в `errors`, полное число — в `error_count`.

## Полнотекстовый поиск в find (0.3.0)

Необязательное поле `content` включает фильтр содержимого **только у fs_find**.
Без него поиск работает как прежде; у list/glob это поле не поддерживается.
Ищутся только обычные файлы: `type` можно опустить или задать `file`.
`type=directory/symlink/other` вместе с content — ошибка входного контракта.

Поиск текста в Python-файлах без учёта регистра:

```json
{
  "path": "/project",
  "name_regex": "\\.py$",
  "content": {"query": "TODO", "ignore_case": true},
  "limit": 50
}
```

Regex в исходниках:

```json
{
  "path": "/project",
  "content": {"query": "(?m)^def\\s+test_", "regex": true},
  "on_error": "skip"
}
```

Явная кодировка и ограничение размера файла:

```json
{
  "path": "/documents",
  "content": {"query": "настройка", "encoding": "cp1251", "max_bytes": 1048576},
  "on_error": "skip"
}
```

| Поле внутри content | По умолчанию | Значение |
|---|---|---|
| `query` | обязательно | Непустая искомая строка или regex |
| `regex` | `false` | При false символы `.*[]` и прочие метасимволы ищутся буквально |
| `ignore_case` | `false` | Unicode-сопоставление без учёта регистра |
| `encoding` | `auto` | Та же схема BOM/UTF-8/эвристика, что у read; либо имя Python codec |
| `max_bytes` | 16777216 | Лимит всего файла, 1–67108864 байт |
| `skip_binary` | `true` | Исключать файлы с NUL в декодированном тексте или auto-входе без BOM |

Совпадение проверяется по полному декодированному тексту, поэтому буквальная
строка может включать переводы строк. Regex использует Python re: `(?m)` включает
многострочные якоря, `(?s)` разрешает точке совпадать с переводом строки.
Размер файла ограничен, но отдельного таймаута регулярного выражения нет;
общий таймаут выполнения задаётся runner. Некорректный regex или неизвестный codec
отклоняется до обхода, даже с on_error=skip и для пустого каталога.

Фильтр содержимого применяется после фильтров метаданных и объединяется с ними
через И. Ответ — прежний SearchResult: каждый подходящий файл появляется один раз,
`total` — число файлов, а не совпадений внутри них. offset/limit/next_offset
применяются к подходящим файлам. Содержимое, фрагменты и номера строк в ответ не
добавляются: для просмотра найденного файла вызовите fs_read.

Бинарность здесь определяется NUL-признаком, это не универсальное распознавание
форматов. Например, UTF-16/32 с BOM корректно декодируются как текст, а файл без
BOM может потребовать явной encoding. При skip_binary=true бинарные кандидаты
исключаются как неподходящие, не увеличивают errors и не делают complete=false.
При skip_binary=false NUL-признак становится ошибкой, подчинённой on_error.

Превышение max_bytes, ошибки чтения и декодирования подчиняются общему on_error:
raise останавливает поиск (по умолчанию); skip записывает виртуальный путь и
диагностику в errors, устанавливает complete=false. Такие файлы не входят в total.
Ограничение max_entries по-прежнему считает все посещённые объекты. Каждый запрос
пагинации выполняет поиск заново; индекс содержимого не создаётся.

Ссылки не читаются. Путь повторно проверяется непосредственно перед открытием
файла; нарушение политики журналируется и останавливает поиск даже с on_error=skip.
Текст запроса и содержимое не добавляются в журнал инцидентов.

## stat

```json
{"path":"/project/main.py"}
```

Пример результата для UTF-8-файла с текстом `hello` и завершающим LF:

```json
{
  "path": "/project/main.py",
  "size_bytes": 6,
  "content_type": "text",
  "line_count": 1,
  "encoding": "utf-8",
  "encoding_source": "utf8",
  "line_ending": "lf",
  "indentation": "none",
  "reason": "decoded_text"
}
```

`size_bytes` — размер в байтах по метаданным файловой системы (включая BOM).
`content_type`: `text`, `binary` или `unknown`; это классификация содержимого,
не MIME-тип и не тип объекта `file/directory`. `line_count` и `encoding` равны
null для binary/unknown. Команда принимает только обычный файл, не каталог/ссылку.

Параметры: `encoding="auto"`, `max_bytes=16777216` (1–67108864).
Auto распознаёт BOM UTF-8/16/32 либо строго декодирует UTF-8. Для cp1251 и других
старых кодировок укажите её явно; эвристическое угадывание read здесь намеренно
не используется, чтобы не объявлять произвольные байты текстом.

```json
{"path":"/documents/legacy.txt","encoding":"cp1251","max_bytes":33554432}
```

Правила определения:

- Известные сигнатуры PNG/JPEG/GIF/ZIP/ELF/GZIP/PDF/WASM дают binary.
- NUL и нетекстовые управляющие символы дают binary; корректный BOM UTF-16/32
  обрабатывается до проверки управляющих символов декодированного текста.
- Успешное полное декодирование без запрещённых controls даёт text.
- Ошибка декодирования даёт unknown, reason=undecodable.
- Файл больше max_bytes не читается: unknown, reason=size_limit, размер в байтах
  всё равно возвращается. Лимит не выдаёт приблизительное число строк.
- Обнаруженное изменение inode/размера/mtime при чтении даёт unknown,
  reason=file_changed. Это не гарантия snapshot при конкурентной записи.

Классификация консервативная, но не универсальный детектор формата: двоичные данные,
состоящие только из печатных UTF-8-символов, неотличимы от текста.
Пустой файл считается text с line_count=0. LF, CRLF и CR разделяют строки;
завершающий перевод строки не добавляет лишнюю строку (`"a\n"` → 1,
`"a\n\n"` → 2), незавершённая последняя строка учитывается.
Unicode U+2028 отдельно строку не разделяет, как и в fs_read.

### Кодировка, окончания строк и отступы (0.5.0)

Эти поля одинаковы у fs_stat и у Entry.stats в list/find/glob с include_stats=true.

| Поле | Значения для text |
|---|---|
| `encoding` | Предполагаемая кодировка auto или явно заданный codec |
| `encoding_source` | `bom` — по BOM; `utf8` — строгое UTF-8 без BOM; `explicit` — задано во входе |
| `line_ending` | `lf`, `crlf`, `cr`, `mixed`, `none` |
| `indentation` | `space`, `tab`, `mixed`, `none` |

При auto кодировка остаётся консервативным предположением: успешное UTF-8
декодирование не доказывает единственную возможную кодировку (например, ASCII
совместим со многими кодировками). Эвристический подбор legacy-кодировки в stat
не добавлялся; для cp1251 используйте encoding/stats_encoding явно. Когда codec
задан явно, encoding_source=explicit даже при наличии BOM.

line_ending относится ко всему прочитанному тексту: CRLF считается одним
разделителем; наличие разных видов даёт mixed. Если переводов строк нет, none.
indentation учитывает только ведущие ASCII-пробелы и табы непустых строк.
Пробельные пустые строки игнорируются; пробелы/табы внутри содержимого строки
не считаются отступом. Смешение в одной строке **или между разными строками**
даёт mixed. Пустой файл и текст без отступов дают none. Размер отступа не оценивается.

Для binary/unknown все три новых поля равны null, как и encoding/line_count.
Если файл превышает max_bytes, частичные предположения о форматировании не выдаются.

Ошибки доступа/отсутствие файла — обычные ошибки TWYLT, а не unknown.
Неверное имя encoding — ошибка запроса. Контроль области/ссылок сохраняется.

### Статы в list / find / glob

```json
{"path":"/project","max_depth":2,"include_stats":true,"limit":20}
```

```json
{"path":"/project","pattern":"**/*.py","include_stats":true,"stats_encoding":"utf-8"}
```

```json
{"path":"/project","content":{"query":"TODO"},"include_stats":true,"stats_max_bytes":1048576}
```

У каждой Entry теперь есть `stats`: объект с полями size_bytes/content_type/
line_count/encoding/encoding_source/line_ending/indentation/reason, либо null. Вложенного path нет: используйте entry.path.
Прежнее поле entry.size по-прежнему возвращается независимо от include_stats.
При include_stats=false, для каталогов и ссылок stats=null; содержимое ради статов
не читается. При true читаются только обычные файлы **возвращаемой страницы**,
а не все совпадения вне offset/limit. Эти статы не меняют состав результатов/total.
Метаданные и stats получаются в разные моменты и могут различаться при записи извне.

stats_encoding и stats_max_bytes независимы от content.encoding/content.max_bytes
полнотекстового поиска. Если нужен один codec для обоих, укажите его в обоих местах.
Файл может читаться дважды: для content-фильтра и затем для статов.
При превышении лимита возвращается stats с unknown, complete остаётся true.
При ошибке чтения и on_error=skip файл **остаётся** в странице со stats=null,
диагностика добавляется в errors, complete=false; on_error=raise прерывает операцию.
Отказы политики области не подавляются и продолжают журналироваться.

## read

```json
{"path":"/work/log.txt","encoding":"auto","offset":100,"count":50}
```

`offset=0` начинает с первой строки. `count` по умолчанию 200, `null` — все оставшиеся строки, `0` — пустой результат без следующей страницы. Строки разделяются LF, CRLF или CR; исходные окончания сохраняются. Конечный перевод строки не создаёт дополнительную пустую строку. Ответ: `text`, `encoding`, `detected`, `offset`, `lines_returned`, `total_lines`, `next_offset`, `path`.

Автоподбор: BOM UTF-32/UTF-16/UTF-8 → строгий UTF-8 → `charset-normalizer`. Эвристика может ошибаться, особенно на коротком тексте; фактически выбранная кодировка возвращается в ответе. Для известных файлов лучше явно задавать `cp1251`, `utf-8`, `utf-16-le` и т.п. Некорректные байты не заменяются молча.

```json
{"path":"/work/legacy.txt","encoding":"cp1251","offset":0,"count":null}
```

`max_bytes` у всех операций чтения по умолчанию 16 MiB, максимум 64 MiB. Ограничение применяется ко **всему файлу**, даже при чтении нескольких строк. Бинарные файлы не являются целевым форматом; NUL без BOM в режиме auto отвергается.

## read_jyt / write_jyt

Чтение:

```json
{"path":"/work/settings.yaml","encoding":"auto","format":"auto"}
```

Ответ: `{ "path": "...", "format": "yaml", "encoding": "utf-8", "data": { ... } }`.

`format`: `auto`, `json`, `yaml`, `toml`. Auto определяется только расширением `.json`, `.yaml`, `.yml`, `.toml`. Для файла без расширения задайте формат явно:

```json
{"path":"/work/settings","format":"json"}
```

Запись:

```json
{"path":"/work/settings.toml","data":{"server":{"host":"127.0.0.1","port":8080}},"overwrite":true}
```

```json
{"path":"/work/settings.json","data":{"enabled":true,"tags":["rtl","test"]},"indent":2,"create_parents":true}
```

Параметры записи: `encoding="utf-8"`, `overwrite=false`, `create_parents=false`, `indent=2` (1…8; JSON/YAML). TOML использует собственный формат отступов. Рекомендуется UTF-8 для всех трёх форматов.

Контракт `data` JSON-совместимый: строковые ключи, массивы, объекты, строки, конечные числа, boolean, null. TOML требует объект в корне и не умеет null. TOML/YAML date/time превращаются в ISO-строки; при обратной записи строки остаются строками. Дублирующиеся ключи, нестандартные YAML-типы, нестроковые ключи, рекурсивные aliases и NaN/Infinity отклоняются. YAML читается SafeLoader; merge-key с повторным ключом также отклоняется. YAML 1.1-поведение PyYAML сохраняется, в том числе преобразование некавыченных `yes/no/on/off` в boolean.

Это чтение и полная сериализация структуры: комментарии, исходный порядок форматирования и YAML anchors при записи не сохраняются. Патча отдельных ключей нет.

## read_markdown

```json
{"path":"/work/README.md","encoding":"auto"}
```

Результат: `path`, `encoding`, `nodes`. Парсер — CommonMark с таблицами и зачёркиванием. Каждый узел содержит `type`, `tag`, `content`, `attrs`, `lines`, `info`, `markup` и при наличии `children`. Закрывающие токены свернуты в дерево. `lines=[start,end]`: начало с нуля, конец не включается; у inline-узлов может быть `null`.

Например, заголовок — узел `heading` (`tag=h1`), внутри `inline`, затем `text`. Списки представлены `bullet_list`/`ordered_list` → `list_item`; fenced code — `fence` с `content` и `info`; ссылки — `link` с `attrs.href`. HTML возвращается как содержимое узлов и не исполняется. Front matter не выделяется, task lists не имеют отдельной семантики, MDX не поддержан. Это AST синтаксиса, а не пересказ или извлечение сущностей.

## write

```json
{"path":"/work/example.txt","content":"Привет\n","encoding":"utf-8","overwrite":false,"create_parents":true}
```

Полная запись без append, автоматической добавки newline и преобразования окончаний строк. Существующий файл требует `overwrite=true`. Конечный симлинк и каталог не могут быть заменены. Сначала формируется временный файл в целевом каталоге, затем публикуется: `os.replace` при замене, `os.link` при создании без перезаписи. Новый файл имеет ограниченные права временного файла (обычно 0600 на POSIX); при замене сохраняются mode-биты прежнего файла, но не гарантируется сохранение владельца, ACL и xattrs. Для создания без перезаписи файловая система должна поддерживать hard links; иначе операция завершится ошибкой. Родительские каталоги могут остаться после неудачной записи.

Ответ записи: `operation`, виртуальный `path`, `changed`, `bytes_written`; `source=null`.

## copy / move

```json
{"source":"/work/src","destination":"/backup/src-copy","create_parents":true}
```

```json
{"source":"/work/old.txt","destination":"/work/new.txt","overwrite":true}
```

`destination` всегда **точное новое имя**, не контейнер: существующий каталог назначения не означает «положить внутрь». `overwrite=false` по умолчанию. При `true` заменяется только существующий обычный файл; слияния/замены деревьев и перезаписи конечных симлинков нет. Симлинки как источник и внутри деревьев запрещены.

Каталоги копируются рекурсивно после проверки всего дерева. Ссылки, специальные
файлы и переходы на другой st_dev отклоняются до начала изменения. Копирование
обычных файлов использует copy2 и временный файл; владельцы/ACL не гарантируются.
При обычной ошибке I/O дерево может остаться частично скопированным.
Move использует shutil.move; проверка не является транзакцией или защитой от
конкурентной замены файлов. Перемещение корня области, в себя/поддерево и
копирование объекта в себя запрещены.

Ответ: `operation`, `path` назначения, `source`, `changed=true`, `bytes_written=null`.

## delete

```json
{"path":"/work/obsolete.txt"}
```

```json
{"path":"/work/build","recursive":true,"dry_run":true}
```

После проверки можно выполнить тот же запрос с `dry_run=false`.

- Пустой каталог удаляется без `recursive`; непустой требует `recursive=true`.
- `missing_ok=false`: отсутствие — ошибка; при `true` успешный ответ с `changed=false`.
- `dry_run=true` проверяет цель и требование recursive, но не гарантирует возможность будущего удаления и выполняет проверку политики для всего вложенного дерева.
- Удаление симлинков и деревьев с симлинками отклоняется до начала изменения.
- Запрещено удаление корня рабочей области, текущего рабочего каталога и его предков.
- Удаление выполняется непосредственно, без корзины и восстановления. При ошибке рекурсивное удаление может быть частичным.

## chmod

```json
{"path":"/project/main.py","mode":"0644"}
```

Предварительная проверка каталога:

```json
{"path":"/project/scripts","mode":"0755","dry_run":true}
```

`mode` — обязательная строка из 3–4 восьмеричных цифр, например `640`, `0755`.
Это полная замена POSIX mode-битов, включая special bits при их указании;
символьные выражения `u+x`, числовой JSON mode и рекурсивный chmod не поддерживаются.
Объект может быть обычным файлом или каталогом. Содержимое каталога не меняется.
Корень рабочей области, ссылки, hardlink-файлы и специальные объекты запрещены.

Результат: `path`, `previous_mode`, `requested_mode`, фактический `mode`,
`changed`, `dry_run`. Mode-строки в ответе нормализованы до четырёх цифр.
Повтор уже установленных прав — changed=false. При dry_run права не меняются,
mode остаётся прежним; проверка не гарантирует, что будущий chmod будет разрешён ОС.
ACL/владельцы/группы отдельно не настраиваются. ОС может ограничить special bits;
ответ показывает фактические права после вызова.

Команда доступна на POSIX. На Windows возвращается явная ошибка: изменение лишь
read-only атрибута не подменяет полноценный chmod. Политические отказы пишутся в
журнал инцидентов; успешное изменение и обычный отказ ОС в доступе не являются
инцидентами политики и не добавляются в её журнал.

## Разработка

```bash
python -m pip install -r requirements-dev.txt
python scripts/export_schemas.py
python -m pytest -q
```

Редактируйте конкретный `tools/*/tool.py` и общий `shared/filesystem_common/common.py`. Генерации встроенных копий больше нет. Тесты сохраняются в проекте для следующих версий. Архитектурные решения — `docs/adr/`. Результаты проверки — `TESTING.md`. Полные схемы каждого инструмента доступны в `schemas` и через describe.

## Интеграция с toolhub-images

После публикации обновите Git ref пака в своём domain YAML и используйте
update: always для замены старого toolset. Сохраняйте весь tools/shared tree.
Образы должны содержать TWYLT >=1.1.1 и внешние зависимости из requirements.txt;
установка самого пака не требуется. Для filesystem обновите соответствующий
source pin в sources.lock.json images, затем пересоберите образы.
Тулы теперь используют общий транспорт и поддерживают TWYLT_ALLOWED_CWD;
legacy override TOOLHUB_RUN_ROOT внутри workspace для этих новых паков больше не нужен.
Не удаляйте собственные настройки data/workspace при обновлении domain.
